## Goals

In this module, you'll run the app, use Github Copilot Modernisation extension to assess it, review the upgrade ,plan and check that the app still works after the upgrade. 

We will be using the todo application in your own workshop repository.

In this module, you wil review and approve the plan before Github Copilot makes changes. In the next module, the automated workflow makes changes first, and you review the pull request.

## Why start with a assessment?

An upgrade changes a dependency and runtime environment, not the application's purpose. The todo list is intentionally small so you can focus on the engineering question: can the application move to a supported Java and framework target while preserving the behavior users rely on? A successful build establishes that the code compiles and packages; creating, completing, and deleting a todo checks a visible behavior that a build alone cannot establish.

The baseline also separates old problems from new ones. If verification already fails before the change, that failure is evidence about the starting revision, not automatically a regression caused by the upgrade. Record it before asking an agent to work, and compare the final result against this same starting point.

## 1. Get and run the app

From your repository's default branch, download the todo app using the setup script from [module 00]({{ site.baseurl }}{% link appmod-lab/0-prerequisites/prerequisite-0-1-technical.md %}):

```powershell
Set-Location -LiteralPath $env:LAB_APP_REPO
& $env:LAB_SETUP -Module todo
git status --short
```

[![VS Code Explorer showing the downloaded src folder with a nested src folder and pom.xml.]({{ '/assets/images/todoapp.png' | relative_url }})]({{ '/assets/images/todoapp.png' | relative_url }})

**What this shows:** The downloaded todo app in VS Code. Expand `src` to find
its `pom.xml` file and source folder. Your other files may look different. The
`U` markers mean Git has not yet tracked those files.

Review the downloaded `src` folder, then commit it to your default branch and push it to your repository. This gives both the interactive and automated exercises the same starting point:

```powershell
git add -- src
git commit -m "Add todo application for workshop"
git push
```

The `src/pom.xml` file uses Java 8 and Spring Boot 2.7.18.

The app is a todo list with web pages generated by the server and a built-in H2 database.

> **Need help?** If you're unsure what to do or see unexpected output, ask
> GitHub Copilot to help you troubleshoot. Share the command you ran and the
> error, but remove any passwords, tokens, or other sensitive information first.
> Review its suggestions before making changes.

First, move into the app folder and check which Java version Maven is using:

```powershell
Set-Location -LiteralPath (Join-Path $env:LAB_APP_REPO 'src')
mvn --version
```

Look for **Java version: 1.8** in the output. If Maven is already using Java 8,
you can continue.

If it shows a different version, find your JDK 8 installation folder in File
Explorer. It is the folder that contains `bin\java.exe`, not the `bin` folder
itself. Copy its full path, replace the example below with your path, and run:

```powershell
$env:JAVA_HOME = 'C:\path\to\your\jdk-8'
$env:PATH = "$env:JAVA_HOME\bin;$env:PATH"
mvn --version
```

Check that Maven now shows Java 8. If you haven't installed it yet, use the
[JDK 8 download]({{ site.baseurl }}{% link appmod-lab/0-prerequisites/prerequisite-0-1-technical.md %})
in the prerequisites. These settings apply to the current terminal only.

Now build the app and run its tests:

```powershell
mvn verify
```

Wait for **BUILD SUCCESS**. If the build or tests fail, note the error and fix it
with copilot before upgrading. This helps you tell an existing problem from one caused by the upgrade.

Start the app:

```powershell
mvn spring-boot:run
```

Wait until the terminal shows `Started TodoApplication`, then open <http://localhost:8080> in a browser. Create a todo, mark it complete, and delete it. Stop the app with Ctrl+C. 

Use sample data only, not customer data.

If port 8080 is already in use, choose another free port, for example 8081:

```powershell
mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=8081"
```

Then open <http://localhost:8081>. Do not stop another application to free its port.

## 2. Create a branch for the upgrade

Check for uncommitted changes with `git status --short`. Save any existing work
before continuing, then create a branch for the upgrade:

```powershell
Set-Location -LiteralPath $env:LAB_APP_REPO
git status --short
$upgradeBranch = "java-upgrade"
git switch -c $upgradeBranch
if ($LASTEXITCODE -ne 0) { throw 'Could not create the upgrade branch.' }
```

Leave your repository's default branch unchanged. The automated workflow in the next
module uses that branch, not the upgrade branch you just created.

## 3. Run an assessment and review the plan

Open your workshop repository in Visual Studio Code. Make sure you're
[signed in to Copilot]({{ site.baseurl }}{% link appmod-lab/0-prerequisites/prerequisite-0-1-technical.md %}#sign-in-to-github-copilot),
then select **GitHub Copilot modernization** in the activity bar.

[![VS Code activity bar with the GitHub Copilot modernization icon outlined in red and an arrow pointing to it.]({{ '/assets/images/GitHub_Copilot_modernization_extension.png' | relative_url }})]({{ '/assets/images/GitHub_Copilot_modernization_extension.png' | relative_url }})

**What this shows:** The red box and arrow mark the icon that opens the modernization panel. The screenshot uses PetClinic; keep your todo repository open for this module. Select screenshot to view it full size.

In the **Quickstart** panel, select **Start Assessment**.

[![Modernization Quickstart panel with Start Assessment above the runtime upgrade, Azure migration, and security actions.]({{ '/assets/images/quickstart.png' | relative_url }})]({{ '/assets/images/quickstart.png' | relative_url }})

**What this shows:** Assessment is the starting point. The other buttons start specific upgrade, migration, or security work; you do not need to run them all. Labels can differ between extension versions.


[![Assessment options showing Recommended Assessment, Custom Assessment, and a link to import a report.]({{ '/assets/images/Assessmentoptions.png' | relative_url }})]({{ '/assets/images/Assessmentoptions.png' | relative_url }})

**What this shows:** You can use a recommended assessment, choose a custom
assessment, or import an existing report. Select a screenshot to view it full size.

Assessment and implementation are different decisions. Assessment gathers facts about the code, dependencies, target compatibility, and tests; a plan proposes changes based on those facts. 



Review the plan before execution because the agent cannot decide which compatibility tradeoffs your users, organization, or release policy will accept. A supported target is not necessarily a drop-in target: runtime, framework, plugins, and libraries must work together, and the newest available version is not a compatibility strategy.

Keep the upgrade bounded. Agree on one target and the behavior to preserve, and
require the plan to identify risks, validation, and a way to recover. This makes
the change reviewable and helps explain unexpected build or test failures instead
of letting scope expand into unrelated modernization.

After reviewing the assessment output, select **Upgrade Java Runtime &
Frameworks**. Choose a supported Java version and a compatible framework version
if needed. Agree on these with the customer. The newest version may not be the
right choice for the app.

Ask Copilot to create a plan before making changes. Review what it will change,
what should keep working, how to test it, any security issues, and how to undo
the upgrade.

You can use this prompt and add the versions you've agreed on:

```text
Run an assessment on the todo app in src for an upgrade to [Java version]
and [framework version]. Keep the existing todo features working. Show me
what needs to change, what might break, which JDKs I need, how to test the
upgrade, and how to undo it. Wait for my approval before making changes.
```

Once you're happy with the plan, approve only the changes you've agreed on and
let Copilot run the upgrade. Follow the
[interactive modernization quickstart](https://learn.microsoft.com/azure/developer/github-copilot-app-modernization/quickstart-upgrade)
if the options in the extension look different.

## 4. Check the changes and test the app

When Copilot finishes, read its summary and check the files it changed:

```powershell
git status --short
git --no-pager diff
```

If Copilot created commits, compare them with your repository's default branch too.
Switch your terminal to the JDK you upgraded to, then return to the `src` folder
and run `mvn verify` as in step 1. Run the app again and check that you can still
create, complete, and delete a todo.

Note the versions used, commands run, results, and anything that still needs
checking or fixing. Don't merge the branch during this exercise. A passing build
or Copilot's summary alone doesn't mean the change is ready to release.

## Checkpoint

You should be able to explain what Copilot found, which plan you approved, what
changed, and whether the app still works. If the upgrade didn't finish, note what
blocked it and keep the error messages for follow-up.
